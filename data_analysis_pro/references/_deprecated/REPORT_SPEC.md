# 数据分析专业报告规范 (REPORT_SPEC.md)

## 总体原则
- **结论先行**：每个章节必须以一句话总结该阶段的核心业务发现。
- **图表互证**：所有提到的关键特征必须配有图表，并紧跟对趋势的业务解读。
- **去技术化**：强制要求在提到专业名词时，嵌入一句话业务解释（术语自动翻译）。
- **实事求是**：严禁虚构未运行的分析步骤，报告必须基于本次真实执行的工件（JSON/PNG）。

## 报告编写前置条件 (Mandatory Inputs)
**在撰写报告前，Agent 必须确保已读取以下工件的内容（如果存在）：**
1. **环境与数据定义**：`env_snapshot.json`, `io_router_output.json`, `metadata_registry.json` (核心业务名来源)。
2. **质量与画像**：`column_profile.json`, `preprocessing_output.json` (记录了清洗血缘)。
3. **线索与发现**：`relationship_screening.json` (提供了 Top N 排名与绘图建议)。
4. **深度分析结论**：`causal_report.json` 或 `baseline_results.json` (核心 ATE 或指标来源)。
5. **准入与评估**：`gate_review.json`, `explainability_report.json` (提供了准入状态与 SHAP 贡献)。

## 叙事分工与逻辑 (Narrative Logic)
1. **脚本定位 (Script)**：`report_export.py` 仅负责**工件汇总、初步翻译、建立骨架**。它产出的 MD 仅作为 Agent 的素材库。
2. **Agent 定位 (Narrative Expert)**：Agent 必须基于脚本产出的素材，结合 `metadata_registry.json` 中的业务语义，按照本规范进行“二次叙事”。
3. **翻译规则**：禁止直接输出 JSON 键值对，必须将其转化为“数值 + 判定 + 意义”的三重解读。
4. **自动验收机制 (Automated Validation)**：必须由验收器（Validator Agent）检查以下红线：是否堆砌了未解释的统计名词？是否缺少因果对比表？是否图文分离？触碰红线则打回重写。

### 1. 摘要与行动建议 (Executive Summary & Action)
- **核心问题 (The Hook)**：明确定义本次分析要回答的业务问题。
- **TL;DR**：3-5 点最核心发现。
- **行动建议**：根据分析结果建议业务方具体“做什么”，而非泛泛而谈。

### 2. 数据健康度报告 (Data Health Audit)
- **质量结论**：数据是否可靠？说明核心清洗动作（如离群值处理）对业务含义的影响。
- **关键指标解释**：如遇到 `missing_rate`，需解释为“数据缺失比例，反映了信息采集的完整性”。

### 3. 特征探索与洞察 (Feature Insights)
- **趋势解读**：严禁只列特征名，必须说明“随着 X 增加，Y 呈现什么趋势，这意味着 [业务含义]”。
- **图表规范**：直接展示 Top N 特征分布图，严禁出现“推荐图表”等占位废话。每张图下必须包含业务建议。

### 4. 深度归因与因果 (Causal & Deep Dive)
- **因果 vs 相关对照表**：在结论前必须包含此表，明确证据等级。

| 发现项 | 证据来源 | 结论等级 | 因果强度 | 建议行动 |
| :--- | :--- | :--- | :--- | :--- |
| A 与 B 强相关 | 关系筛查 | `exploratory` | **相关性** (无干预识别) | 仅作为观察性参考 |
| C 对 Y 有显著影响 | 因果分析 (PSM/IV) | `report-ready` | **中强因果** (已控混杂) | 可作为业务干预切入点 |
| 预测 D 准确率 85% | 基线模型 | `report-ready` | **预测相关** (无因果推断) | 用于预警，不用于直接归因 |

- **因果结论**：用“如果我们将 X 改变 1 单位，Y 会改变多少”来描述。

### 5. 可信度与局限性 (Trust & Limitations)
- **叙述等级**：明确报告是 `report-ready`（可决策）、`exploratory`（需跟进）还是 `not_usable`（不可信）。
- **局限性**：诚实说明数据量或噪声导致的不确定性。

## 强制性编写指南

### 1. 术语自动翻译 (Terminology)
凡出现统计/AI名词，必须紧跟一句“人话”解释。
- *示例*：`p-value < 0.05`（统计显著性指标，说明观察到的结果极大概率不是随机巧合）。

### 2. 数值深度解读 (Value Triple-Interpretation)
对关键数值（如 R2, ATE, F1）进行“好/坏/意义”三重解读：
- **指标名与数值**：展示具体数值。
- **好坏判定**：对比 Baseline 或业务基准，明确当前表现。
- **业务意义**：解释该数值对决策的直接影响。
- *示例*：`ATE = 5.2%`。含义：干预带来的平均处理效应。判定：优于去年 3% 的基准。意义：建议全面推广该营销策略，预计可提升总营收约 5%。

### 3. 图表交互规范 (Chart Interaction)
- **禁止废话**：严禁“下图展示了关系”、“建议查看图表”等表述。
- **图表配解读**：图表下方必须紧跟自然语言，第一段说明“图里有什么”，第二段谈“业务建议是什么”。
- **图题中文**：所有工件引用必须配有准确的中文标题。

### 4. 交付防护
- **证据回指**：每个判断都应指回具体工件（如 `baseline_results.json`）。
- **叙述降级**：若脚本运行失败或样本不足，结论必须降级为 `exploratory` 或 `not_usable`，不得补写结论。
