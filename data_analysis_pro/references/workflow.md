# 数据分析专业版：建议工作流

## 当前定位

这份文档提供的是“推荐分析顺序”，不是强制 pipeline。

`data_analysis_pro` 的目标是让 Agent 按问题自由组合原子能力，而不是要求每次都走同一条固定路线，更不是要求生成 checkpoint、状态文件或统一中间工件。

## 1. 先说清问题

开始前先尽量确认这些最小问题：

- 目标是什么
- 每一行代表什么
- 哪些字段共同定义一条“唯一业务记录”
- 核心指标是什么
- 时间范围或业务范围是什么
- 当前更像描述、预测，还是因果/实验问题

如果这些信息不完整，也不必停在原地，但要在分析里显式写出假设。

## 2. 先读数据，再谈方法

推荐先做两件事：

- 用 `io_router.py` 确认输入能否被稳定读取
- 用 `column_profile.py` 看字段类型、缺失、高基数、常量列和潜在目标列

这一阶段的目标不是“立刻建模”，而是先判断：

- 数据口径是否像你以为的那样
- 哪些字段像 ID、流水号、结果后变量
- 是否已经存在明显的质量问题

## 3. 只在需要时做预处理

如果列画像已经暴露问题，再用 `preprocessing.py` 或小段自定义代码做轻量处理。

常见动作包括：

- 删除明显无意义列
- 处理缺失
- 去重
- 基础编码

不要默认把预处理写成“大而全的特征工程阶段”；当前 skill 更适合按问题最小化处理。

去重时额外注意：

- “完全相同的两行”不一定等于脏数据，可能只是缺少实体 ID 后的真实重复观测。
- 优先先检查业务键重复，再决定是否删除。
- 如果拿不准，就先在结果里报告重复规模和可能口径，不要直接清洗掉。

## 4. 先做探索，再决定是否深挖

在很多任务里，先做下面这些已经足够有价值：

- `eda_stats.py`
- `relationship_screening.py`
- 必要的分组统计和可视化

这一步常常能回答：

- 哪些变量值得继续看
- 是否存在明显分层
- 是否已经足够支撑业务讨论

如果这里只得到弱线索，也可以直接交付探索性结论，而不是强行进入更复杂路径。

## 5. 预测路径：先基线，后结论

只有在满足下面条件时，才值得进入预测性分析：

- 目标列清晰
- 样本量和字段质量基本可接受
- 没有明显泄露风险

进入后，建议先做 tabular baseline。

现实边界要写清楚：

- `baseline_runner.py` 当前更适合作为 Python helper 调用，不是稳定 CLI
- `gate_evaluator.py` 也是判断助手，不是完整治理系统

所以推荐做法是：

- 先拿到一份可信的 baseline 结果
- 再决定是否值得继续解释、汇报或扩展

## 6. 因果/实验路径：只有在脚本真能跑通时再走

`data_analysis_pro` 里保留了实验与因果方向的参考文档，但当前对应脚本并不是最稳定的部分。

因此正确用法是：

- 先确认脚本、依赖和输入条件都满足
- 再进入实验或因果分析
- 如果没跑通，就明确降级成“方法建议 / 待验证项”，不要补写成结果

## 7. 交付默认是 Markdown + 证据链接

当前更稳妥的交付方式通常是：

- 一个清晰的 Markdown 结论
- 附上关键 JSON / PNG / 中间结果路径
- 明确写出限制、风险和下一步

不要默认假设存在统一 dashboard、正式报告导出器或 checkpoint 恢复系统。

## 8. 什么时候该停下来并汇报

以下情况通常应停止继续复杂化，而转成“诚实交付当前发现”：

- 数据口径本身不成立
- 关键字段严重缺失
- 泄露风险无法排除
- baseline 没有明显优于 dummy
- 复杂方法脚本未形成可复核结果

这时最好的输出不是“再造流程”，而是：

- 现在能确认什么
- 现在不能确认什么
- 下一步最小需要补什么

## 防护准则

- 不要因为有很多 reference，就把分析做成 SOP。
- 不要为了显得完整而强行经过每个阶段。
- 不要把“当前能自由组合”重新写成“必须按序执行”。
- 如果某一步没有新增证据，就可以停在前一步。
